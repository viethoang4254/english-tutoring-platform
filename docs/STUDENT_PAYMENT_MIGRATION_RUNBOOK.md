# Supabase V6 to V10: payment migration procedure

This is an operator runbook. Keep application Flyway startup disabled. Schedule live execution separately after CI succeeds and the database owner approves the target, backup and recovery window.

1. **Identify and inspect.** Verify the Supabase project and database over TLS. In a read-only transaction inspect public.flyway_schema_history (version, script, checksum, success, installed_rank), required tables, columns, indexes, foreign keys and triggers. Compare V1–V6 checksums with the accepted release. Stop on drift, partial objects, failed history, or a different baseline.
2. **Capture and verify a recovery point.** Quiesce all application writers, including enrollment, receiving-account reviews and financial operations. Record the UTC cutoff. Confirm a backup/PITR point covers it and perform a restore rehearsal on a separate, access-controlled staging database. Record aggregate counts and compare account IDs, payment-to-enrollment and receiving-account references, amount/status snapshots, and enrollment states inside trusted storage. Keep banking data and dump credentials out of logs. Database backups do not back up private Storage image objects; verify their backup and access separately if present.
3. **Rehearse in order.** Use the release's Flyway binary/configuration and exact migration files on the restored copy. Run Flyway validate/info before and after, limiting the target to V10. Review each stage:
   - V7__teacher_payment_account_submission.sql preserves legacy IDs/bank codes, marks legacy accounts UNREVIEWED and removes ACTIVE selection. It adds submission/QR evidence, idempotency and one-PENDING constraints. Existing Teachers may need a new submission and authorized review before receiving new payments.
   - V8__teacher_payment_account_review.sql adds reviewer FK, timestamp, rejection reason and terminal-decision guards. A pre-existing reviewed row without authentic metadata must block migration. Never manufacture approval history.
   - V9__payment_monetary_snapshot.sql classifies historical payments as LEGACY, widens discount precision, and enforces the new VND rounding policy and immutable receiving/QR snapshots. Check existing amounts against the legacy constraint before migration. Do not recalculate history or generate QR data for legacy payments.
   - V10__manual_payment_reconciliation.sql adds payment_reconciliation_attempts, allocation uniqueness and append-only UPDATE/DELETE/TRUNCATE guards. Historical confirmation is not backfilled as Teacher attestation.
4. **Approved live window.** With writers still paused and the verified recovery point available, use a single authorized Flyway migrator with target 10. Apply V7 → V8 → V9 → V10. On error stop immediately, record the failing version and sanitized SQLSTATE, inspect history and actual objects read-only. Earlier successful migrations can remain committed. Do not blindly retry, repair checksums, drop constraints, or clean the schema. Keep writes paused; obtain approval for a reviewed forward fix or restoration to the verified pre-window point.
5. **Validate before reopening.** Require ten successful versioned migrations with matching checksums and 24 expected application tables (exclude Flyway history). Verify the new constraints, triggers and unique indexes are present and enabled; compare the pre-window counts, snapshots and references, allowing only documented legacy classification/selection changes. Verify zero unintended payment confirmations, enrollment activations or invented attempts. Verify owner-only read paths and anonymous denial on staging; exercise writes and concurrent reconciliation only on disposable fixtures. Confirm receiving-account eligibility and private Storage configuration before enabling new payment requests. Record results and obtain operator sign-off before resuming writes.
